# Zig build of the ZetaSQL analyzer

This directory, together with the top-level `build.zig`, builds the vendored
ZetaSQL C++ sources (`internal/ccall`) with the Zig toolchain — no Bazel, no
cgo — and produces a small demo binary that calls the ZetaSQL analyzer.

## Layout

| File | Purpose |
| ---- | ------- |
| `../build.zig` | Compiles the vendored tree into static libraries (`zetasql`, `absl`, `icu`, `re2`, `protobuf`, `support`) and links the demo executable. |
| `analyzer_smoke.cc` | C ABI shim over `zetasql::AnalyzeStatement` (Zig cannot call C++ directly). |
| `main.zig` | Demo binary: analyzes a SQL statement and prints the resolved AST. |

## Usage

Requires Zig 0.14.1.

```
zig build                          # builds zig-out/bin/zetasql-analyzer-demo
zig build run                      # analyzes the default statement
zig build run -- "SELECT CONCAT('a', 'b')"
```

Example output:

```
analyzed OK:
QueryStmt
+-output_column_list=
| +-$query.three#1 AS three [INT64]
+-query=
  +-ProjectScan
    ...
```

## How the source lists are derived

`build.zig` walks `internal/ccall` at configure time rather than hardcoding
~640 file paths:

- **zetasql**: everything except tests, testdata, tooling, compliance,
  scripting, `reference_impl`, plus a small set of extra files the resolver
  needs from otherwise-excluded directories (see `extras` in `build.zig`).
  `anonymization_utils.cc` is skipped because the differential-privacy
  library it needs was never vendored; the `type_modifiers` pair is skipped
  because it was generated by a newer protoc than the vendored runtime.
  Neither is referenced by anything the analyzer links.
- **protobuf**: the vendored tree mixes files from several protobuf
  versions, so the list is parsed out of `go-protobuf/protobuf/export.inc` —
  the same curated list the cgo build compiles.
- **absl / icu / re2**: directory walks with test/benchmark exclusions.

Because everything is linked as static archives, the linker only pulls the
objects the analyzer actually needs.

## Getting Zig in sandboxed environments

Dev sandboxes whose network egress cannot reach ziglang.org can use the
temporary `zig-toolchain` GitHub Actions workflow: it downloads the official
Zig 0.14.1 tarball (checksum-pinned upstream) on a CI runner and force-pushes
it to the `tmp/zig-toolchain` branch, from which a sandbox can fetch it via
the repo remote:

```
git fetch origin tmp/zig-toolchain --depth 1
git archive FETCH_HEAD | tar -x -C /path/to/toolchain
tar -xf /path/to/toolchain/zig-x86_64-linux-0.14.1.tar.xz -C /path/to/toolchain
```

Both the workflow and the branch are safe to delete once no longer needed.
